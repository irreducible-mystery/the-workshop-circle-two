## THE LAST FINDING — a pin that is not a pin, in the pin table

The close document prepared for the project's map carries this for the
artifact:

```
project doc : 6a6b6cb21ff89b9b533151ce6f3ee0370d3206c9632192f0920d5da0d4560c0   (63 chars)
the record  : 6a6b6cb21ff89b9b533151ce6f3ee0370d3206c9632192f0920ad5da0d4560c0   (64 chars)
equal       : False
```

**A SHA-256 is sixty-four hex characters. That one is sixty-three.** It
is not a wrong pin; it is not a pin at all — one character was lost
somewhere between the record and the page, and the result cannot match
anything, ever, including the file it names.

The builder's own table hedged it correctly — *see v3/VIEWS for the
authoritative value* — which is the right instinct and is why this is
reported rather than convicted. But the hedge is doing work the pin
should be doing, and the document it sits in is **the map a Circle Four
reads first.** A new seat verifying its inheritance against that table
would measure the artifact, find no match, and have to work out from
scratch whether the record moved or the pin was mangled. This circle
spent its round-one handshake doing exactly that, over exactly this
kind of defect, and named it crop item C1.

The record's own copies are correct and are the authority: `VIEWS.md`
renders the artifact's pin from the artifact, and `STATE-OF-THE-RECORD-v3.md`
points at `VIEWS.md` rather than retyping it (norm 19), which is
precisely why neither could carry this defect. **Norm 19 was bought to
stop stale counts and it stopped a mangled pin** — the mechanism
guarding what it names, one class wider than it was written for.

Offered, not ruled: the fix is one character in a document outside this
record, and it belongs to the seat that holds that document.
